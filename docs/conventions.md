# Conventions

## TypeScript

- `strict: true`, plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
- No `any`. Use `unknown` and narrow.
- No non-null assertions (`!`) outside test files.
- No `as` casts except immediately after a Zod parse at an external boundary.
- Types are inferred from Zod schemas (`z.infer<typeof X>`), never declared in parallel.
- Prefer discriminated unions over optional-field soup:

```ts
type Assessment =
  | { verdict: 'eligible'; confidence: number; evidence: Evidence[] }
  | { verdict: 'not_eligible'; confidence: number; reason: RuleId; evidence: Evidence[] }
  | { verdict: 'needs_review'; confidence: number; openQuestions: string[] }
```

## Errors

Domain code returns typed results; it does not throw for expected failures.

```ts
type Result<T, E = DomainError> =
  | { ok: true; value: T }
  | { ok: false; error: E }
```

Throw only at edges (route handlers, worker entry points) where a framework catches it.
Never swallow an error to keep a pipeline moving — record it and mark the record failed.

## Validation

Every external input is parsed with Zod at the boundary it enters: HTTP responses, LLM
outputs, form bodies, env vars, queue payloads. Inside a module, data is already typed
and is not re-validated.

Env vars are parsed once in `src/lib/env.ts`, on first use, and read through
`getEnv()`. Never `process.env.X` outside that file. Parsing on first use rather than on
import means importing a module never requires the runtime configuration (drizzle-kit,
pure unit tests, `next build`).

## Naming

- Files: `kebab-case.ts`. React components: `PascalCase.tsx`.
- Database: `snake_case` tables and columns, plural table names.
- Booleans read as assertions: `isEligible`, `hasAuthorization`, `requiresRelocation`.
- Avoid `data`, `info`, `item`, `handle`, `process`, `manager`, `helper`, `util` as names.
- A name that needs a comment to explain it is the wrong name.

## Database

- Every table except `users`, `jobs`, `raw_jobs`, `job_sources`, and
  `job_posting_snapshots` carries `user_id` with an index, and declares
  `tenantIsolation()` in its `schema.ts` (decision 0004).
- Service functions take the executor as their first argument: `Db` for the shared
  catalog, `TenantScope` for per-user tables. Callers own transaction boundaries, so one
  transaction can span modules.
- Enum-like columns are `text` plus a CHECK built from the same `as const` tuple as the
  Zod enum. Postgres enums can't drop or rename values in place.
- Timestamps are `timestamptz`, always UTC, named `*_at`.
- Money is stored as integer minor units plus a currency code: `bigint` columns, with
  model costs in integer micro-USD. Never floats.
- Migrations are generated by Drizzle and committed. Never hand-edit an applied one.
- Additive changes are safe; anything destructive needs a decision record.

## Testing

Test-first for: eligibility rules, dedupe fingerprinting, grounding validation, question
classification, and salary parsing. These are the parts where a silent wrong answer is
expensive.

Not test-first (test after, or not at all): UI components, CRUD passthroughs, adapters
beyond one fixture-based happy path and one malformed-payload case.

- Unit tests sit beside the code as `*.test.ts`.
- Database tests use the `dbTest` fixture (`src/lib/db/testing.ts`). It runs against real
  Postgres as the app role, inside a transaction that is rolled back afterwards.
- Adapter tests run against committed fixture JSON, never the live network.
- LLM-calling code is tested with a stubbed `callModel`. The real model is exercised only
  by the eval suite.

## LLM code

- One named, versioned task per call site (`eligibility.extract@v3`).
- Prompts live in `src/modules/<module>/prompts/<task>.ts` as exported template
  functions, never inline in business logic.
- Every call declares a Zod output schema.
- Every call's trace (task, version, model, tokens, cost, latency, raw output) is stored
  against the record it produced.
- A validation failure retries once with the error appended, then fails the record. It
  never falls back to a guessed value.

## Git

- Branch per milestone: `m1.4-greenhouse-adapter`.
- Commit messages: imperative subject under 70 chars, body explaining *why*.
- A PR description states: what changed, what decision was made that the task brief did
  not specify, and the output of `pnpm typecheck && pnpm test && pnpm lint`.
- Migrations are committed in the same PR as the schema change that generated them.

## Comments

Explain why, never what. Delete any comment that restates the code. A `TODO` must name
the milestone that resolves it or it does not get committed.
