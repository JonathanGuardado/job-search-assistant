## Task: Track applications: log one from a job, move it through stages, keep the posting

**Milestone:** 1.9
**Read first:** `AGENTS.md`, `docs/conventions.md`, `docs/architecture.md` (Modules, Module contract), `docs/domain-model.md` (sections `applications`, `application_events`, `job_user_states`), `docs/decisions/0012-application-tracking.md`, `docs/decisions/0004-tenancy-rls.md`

### Goal

After this task the owner can mark a job "applied" from its page, recording the date, the resume version sent, the salary asked, a contact and notes. They can then follow the application through its stages, each change dated and kept in a history that cannot be rewritten, and read the posting exactly as they applied to it, even after the company takes it down. This is the last milestone of phase 1: it turns the jobs view into a search the owner can run end to end.

### Implementation notes

**Service** (`src/modules/applications/service.ts`). Every function takes the `TenantScope` (or `Db`) first, returns `Result` for expected failures, and never throws for them. Map rows to `Application` with `salaryAsked` built from the two salary columns (both null → null).

- `createApplication(scope: TenantScope, input: NewApplication): Promise<Result<Application>>`
  1. `getJob(scope.db, input.jobId)`; a missing job → `not_found`.
  2. `input.appliedOn` later than today's UTC date → `invalid_input` "The application date cannot be in the future."
  3. When `resumeId` is not null, `getResume(scope, resumeId)` must succeed; otherwise `not_found` "That resume version was not found."
  4. An existing application for this job and user → `conflict` "You already logged an application for this job."
  5. `getJobRawVersion(scope.db, jobId)` for `rawJobId`.
  6. Insert the application with status `applied` and `sourceUrl` = `input.sourceUrl ?? job.applyUrl`; insert one event (`fromStatus` null, `toStatus` `applied`, `occurredOn` = `appliedOn`, `note` = null); call `setJobUserState(scope, { jobId, state: 'applied' })`. All three use `scope.db`, so they commit together.
- `changeStatus(scope: TenantScope, input: StatusChange): Promise<Result<Application>>`
  - Missing (or another user's) application → `not_found`. `to` equal to the current status → `invalid_input` "It is already <status>." `occurredOn` in the future → `invalid_input`; before `appliedOn` → `invalid_input` "A change cannot happen before the application was sent."
  - Update `status` and `updatedAt` (`sql\`now()\``), and insert the event `{ fromStatus: current, toStatus: to, occurredOn, note }`, both on `scope.db`.
- `updateApplication(scope: TenantScope, applicationId: string, edit: ApplicationEdit): Promise<Result<Application>>`
  - `not_found` as above; the same future-date and resume checks as create. Updates the editable fields and `updatedAt`. It does not change `status` and writes no event: history records stage changes only. Changing `appliedOn` does not alter the first event.
- `listApplications(scope: TenantScope): Promise<ApplicationListItem[]>` where `type ApplicationListItem = Application & { lastActivityOn: string }`, the latest `occurredOn` among its events. Ordered by `lastActivityOn` newest first, then `createdAt` newest first.
- `getApplication(scope: TenantScope, applicationId: string): Promise<Result<{ application: Application; events: ApplicationEvent[] }>>`: events oldest first by `occurredOn`, then `recordedAt`.
- `getApplicationForJob(scope: TenantScope, jobId: string): Promise<Application | null>`
- `postingAsApplied(db: Db, application: Pick<Application, 'rawJobId'>): Promise<Result<NormalizedPosting>>`: `readNormalizedPosting(db, application.rawJobId)`.

The tenant filter is enforced by RLS, but write each query with an explicit `userId = scope.userId` condition as well, as `jobs.getJobUserState` does, so it reads correctly on its own.

**The job page, `/jobs/[jobId]`.** Below the eligibility and match sections, add an "Your application" section:
- If `getApplicationForJob` returns one: "Applied on <appliedOn> · <status label>" and a link "Open application" to `/applications/<id>`. No form.
- Otherwise a form posting to `logApplication`, with:
  - `appliedOn`: a date input, default today's UTC date, `max` today
  - `resumeId`: a select of `listResumes` ("Version <version> · <filename>", newest first, the newest selected) plus "Not one stored here" (empty value)
  - `salaryAmount`: a text input, and `salaryCurrency`: a select of `CURRENCIES` defaulting to the profile's `salaryCurrency` (USD without a profile)
  - `contactName`, `contactEmail`, `contactUrl`: text inputs
  - `notes`: a textarea
  - `sourceUrl`: a text input with the placeholder showing `job.applyUrl`; empty means the job's link
  - submit "Mark applied"

**The jobs list.** In `JobRow` and the job page badges, show "Applied" when the user state is `applied`. In `JobActions`, when the state is `applied`, render no Save, Unsave, Hide or Unhide button (they would overwrite the applied state); keep "I can take this" and "Undo my verdict" as they are.

**The applications list, `/applications`.** Query parameter `status`: an `ApplicationStatus` or `all` (default `all`), parsed with Zod; invalid falls back to `all`. Load `listApplications`, then `getJobs` for their job ids. Show a status filter (links, each with its count over all applications), then one row per application: company, title (linked to `/applications/<id>`), status label, "Applied <appliedOn>", "Last activity <lastActivityOn>", and "Posting taken down" when the job's `closedAt` is not null. Empty state: "No applications yet. Mark a job applied from its page."

**The application page, `/applications/[applicationId]`.** Validate the id as a UUID; a missing application calls `notFound()`. Show:
- Company and title (from `getJob`), status label, applied on, the resume ("Version <version> · <filename>" from `getResume`, or "Not one stored here"), salary asked (`salaryToInput` plus the currency, or "Not stated"), contact, source URL as a link (`target="_blank" rel="noopener noreferrer"`), notes, outcome reason.
- "Change stage": a form posting to `changeApplicationStatus` with a select of the other statuses, `occurredOn` (date, default today, `max` today, `min` appliedOn) and an optional `note`.
- "History": every event, oldest first: "<occurredOn> · <from label> → <to label>" ("Logged as applied" for the first), the note, and "recorded <recordedAt date>" when it differs from `occurredOn`.
- "Edit details": a form posting to `editApplication` with the same fields as the create form plus `outcomeReason`, prefilled.
- "The posting as you applied to it": from `postingAsApplied`. Its title, location and full `description` as preformatted text (`white-space: pre-wrap`), never as HTML. When the job is closed: "This posting is no longer listed. This is the version you applied to." If `postingAsApplied` fails, show its error message instead of the section's text.

Status labels: applied "Applied", interviewing "Interviewing", offer "Offer", accepted "Accepted", rejected "Rejected", withdrawn "Withdrawn", no_response "No response".

**Server actions** (`src/app/applications/actions.ts`, `'use server'`): `logApplication`, `changeApplicationStatus`, `editApplication`. Turn the form into the module's input and parse it with `NewApplicationSchema`, `StatusChangeSchema` or `ApplicationEditSchema`:
- empty strings become null (or absent for contact fields); a contact with no field set becomes null
- `salaryAmount` goes through `salaryFromInput(amount, currency)`: an error is reported, an empty amount means `salaryAsked` null
On success, `logApplication` redirects to `/applications/<new id>` and the other two to the application page. On a parse failure or a failed `Result`, redirect back to the form's page with `error=<message>`, shown in a `role="alert"` element. Never call `redirect` inside a `try` block.

**Style.** Follow `src/app/jobs/jobs.module.css` and `src/app/settings/settings.module.css`. Plain CSS modules, server components, forms that work without client JavaScript. Both new pages declare `export const dynamic = 'force-dynamic'`.

### Tests required

`src/modules/applications/service.test.ts`, using the `dbTest` fixture (`src/lib/db/testing.ts`) and `test-fixtures.ts`:

- create: returns the application with status `applied`, the job's `rawJobId` and `applyUrl`; writes one event from null to `applied` on `appliedOn`; sets the job's user state to `applied`.
- create: `conflict` the second time for the same job; `not_found` for a missing job; `invalid_input` for tomorrow's date; `not_found` for a resume id that is not the candidate's.
- changeStatus: moves `applied → interviewing → rejected → interviewing`, writing one event per move, in order, with the notes; refuses the current status, a future date, and a date before `appliedOn`; `not_found` for another candidate's application.
- updateApplication: changes notes, contact, salary and outcome reason without writing an event or changing the status.
- listApplications: orders by latest activity; `lastActivityOn` is the latest event's day.
- isolation: one candidate's applications are invisible to another in `listApplications`, `getApplication` and `getApplicationForJob`.
- postingAsApplied: after `takeDown`, the job is closed and `postingAsApplied` still returns the posting's title and description.

UI components and server actions are not tested (`docs/conventions.md`).
