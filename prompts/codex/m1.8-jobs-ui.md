## Task: Build the jobs view: tabs by eligibility, ordered matches, and the job card

**Milestone:** 1.8
**Read first:** `AGENTS.md`, `docs/conventions.md`, `docs/architecture.md` (Modules, Module contract), `docs/domain-model.md` (sections `eligibility_assessments`, `match_assessments`, `job_user_states`, `jobs`), `docs/decisions/0009-eligibility-pipeline.md` (D10, D11), `docs/decisions/0010-matching-pipeline.md`

### Goal

After this task the owner opens `/jobs` and sees every open job the system assessed for them, split into five tabs by what eligibility decided, with the jobs they can take first and the closest matches at the top of each tab. Each job opens into a page that shows why it is in its tab (the eligibility verdict with its evidence) and how it matches (the job card). The owner can save or hide a job and overrule a verdict. This replaces LinkedIn for their search, so every line must come from stored data: the view computes no verdict and no score of its own.

### Implementation notes

**Both pages** declare `export const dynamic = 'force-dynamic'`, as `src/app/settings/page.tsx` does: the data changes with every worker run.

**The list, `/jobs`.** Query parameters: `tab` (a `ReviewGroup` or `hidden`; default `can_apply`), `page` (1-based; default 1), `company` (free text; default empty). Parse them with Zod; an invalid value falls back to its default, never an error page.

Load, all in one request, in this order: `listAssessments`, `listJobUserStates`, `listMatches` (each inside one `withTenant(getDb(), DEV_USER.id, ...)`), then `getJobs(db, <every assessed job id>)`. Then call the pure function below and render its result. No other reads.

`src/app/jobs/_lib/job-list.ts` exports `buildJobList(input)` and its types. It takes the assessments, jobs, matches, user states, `tab`, `page`, `company`, and returns `{ tabs: { key, label, count }[]; rows: Row[]; page; pageCount }`. It must:

1. Keep only jobs that are open and canonical (`closedAt === null && canonicalJobId === null`) and have an assessment. A job whose user state is `ignored` belongs only to the `hidden` tab.
2. Put every other job in the tab `reviewGroup(assessment)` returns.
3. Count each tab after rules 1–2 and before the company filter.
4. Filter the current tab by `company`: case-insensitive substring of `companyName`, after trimming; empty matches everything.
5. Order by `compareForReview(matchOf(a), matchOf(b))`, then `postedAt` newest first (null last), then `id`.
6. Page at 50 rows. `pageCount` is at least 1. A `page` past the end returns the last page.

Tab labels, in `REVIEW_GROUPS` order, then hidden: `can_apply` "Can apply", `needs_review` "Needs review", `location_only` "Probably onsite", `visa_unknown` "Needs a visa", `not_eligible` "Not eligible", `hidden` "Hidden". Show each count in the label: "Can apply (12)".

Under the tabs, one line per tab, verbatim:
- `can_apply`: "Jobs whose posting shows you can take them, or that you marked yourself."
- `needs_review`: "The posting leaves something open. Each job says what."
- `location_only`: "The posting names a place but never says remote, hybrid or onsite. Not matched unless you mark it."
- `visa_unknown`: "You would need work authorization there, and the posting does not say whether it sponsors visas. Not matched unless you mark it."
- `not_eligible`: "The posting rules you out. Each job quotes the sentence that does."
- `hidden`: "Jobs you hid. They appear nowhere else."

Then, above the rows, `REVIEW_ORDER` as a sentence, so the order is never a hidden score.

Each row shows:
- Company, title (linked to `/jobs/<id>`), location (`locationText`, or "Location not stated").
- Salary: `formatSalary(job.salary)` (below), or "Salary not stated".
- When a match exists: "<requiredShown> of <requiredTotal> required skills shown" (omit when `requiredTotal` is 0), and `topConcern` when not null.
- When no match exists: the eligibility reason. For `not_eligible`, `reasons.reason`; for a review, the first of `reasons.openQuestions`. For an eligible job with no match yet: "Not matched yet."
- Badges: "Saved" when the user state is `saved`; "Your verdict" when `userOverride` is not null.
- Buttons, each a `<form>` posting to a server action with hidden `jobId` and a hidden `back` URL (the current URL, so the tab, page and filter survive): "Save" or "Unsave"; "Hide" (or "Unhide" in the hidden tab); "I can take this" on every tab except `can_apply`; "Undo my verdict" when `userOverride` is not null.
- Pagination links (previous, next, "Page N of M") that keep `tab` and `company`.
- A company filter: a GET form with one text input named `company` and a hidden `tab`.

**The job page, `/jobs/[jobId]`.** Validate `jobId` as a UUID; anything else, or a job with no assessment for the dev user, calls `notFound()`. Show:
- Company, title, location, salary (and `salaryQuote` beneath it in quotes, labeled "From the posting", when not null), a link to `applyUrl` that opens in a new tab with `rel="noopener noreferrer"`.
- The eligibility section: the tab label of `reviewGroup`; the engine's verdict; for `not_eligible`, `reasons.reason`; for a review, every open question; every `evidence` quote, as a quotation. When `userOverride` is set: "You marked this: <verdict>" with `overrideReason` when present.
- The match section: from `getMatchCard`. If null, "Not matched yet." Otherwise `match.concerns` as a "Before you apply" list, then each section's headline with its details beneath. Use `CardSection.status` only to pick a marker: meets ✓, partial ~, gap ✗, unknown ?, not_stated ·.
- The same buttons as the list. "I can take this" here also offers an optional reason: a text input named `reason`, at most 500 characters.
- The full `description` at the bottom, as preformatted text (`white-space: pre-wrap`). Never render it as HTML.

**Server actions** (`'use server'`, in `actions.ts`). Parse the form with Zod: `jobId` a UUID; `back` must start with `/jobs` (otherwise use `/jobs`); `reason` optional, trimmed, at most 500 characters. Every action ends in `redirect(back)`. On a failed `Result`, redirect to `back` with `error=<message>` appended (`?` or `&` as needed), and show that message on the page in a `role="alert"` element. Never call `redirect` inside a `try` block.
- `saveJob`/`unsaveJob`: `setJobUserState` with `saved`/`new`.
- `hideJob`/`unhideJob`: `setJobUserState` with `ignored`/`new`.
- `markEligible`: `setUserOverride` with verdict `eligible` and the reason, then `queueMatchNow(getDb(), getEnv().REDIS_URL, { userId: DEV_USER.id, jobId })`. If the queue call fails, the override is still saved: redirect with its error message.
- `undoVerdict`: `setUserOverride` with verdict `null` and reason `null`.

**Formatting** (`format.ts`). `formatSalary(salary)` returns null for an unknown salary. For a posted one, it divides by 10^(the currency's minor digits), taken from `new Intl.NumberFormat('en', { style: 'currency', currency }).resolvedOptions().maximumFractionDigits`, and formats with `Intl.NumberFormat('en', { style: 'currency', currency, maximumFractionDigits: 0 })`. Both bounds: "$143,000–$190,000"; min only: "From $143,000"; max only: "Up to $190,000". Use an en dash.

**Style.** Follow `src/app/settings/settings.module.css`: same page frame, fonts, colors and button look. Plain CSS modules; no new styling system. The pages must work without client JavaScript. Do not add `'use client'` components, except where a form genuinely cannot work without one; none is needed here.

### Tests required

UI components are not tested (`docs/conventions.md`). The two pure files are:

- `buildJobList`, grouping: an eligible, a needs-review, a location-only, a visa-unknown and a not-eligible assessment land in their five tabs; a `not_eligible` assessment with `userOverride: 'eligible'` lands in `can_apply`.
- `buildJobList`, hiding: a job with state `ignored` is only in `hidden`, and no other tab counts it.
- `buildJobList`, exclusion: a closed job, a linked duplicate (`canonicalJobId` set) and a job without an assessment appear nowhere.
- `buildJobList`, counts: counts ignore the company filter; the filter is case-insensitive and trims.
- `buildJobList`, order: a match with role `meets` comes before `partial`, which comes before an unmatched job; equal matches order by `postedAt`, newest first, null last.
- `buildJobList`, paging: 51 jobs give two pages; page 2 has 1 row; page 99 returns page 2; an empty tab gives `pageCount` 1 and no rows.
- `formatSalary`: USD both bounds, min only, max only, unknown → null, and JPY (zero minor digits): `{ minMinor: 5_000_000, maxMinor: null, currency: 'JPY' }` → "From ¥5,000,000".

Build the test inputs as plain objects of the types above. Do not touch the database in these tests.
